Formal methods · Specula · srsRAN Project vs OCUDU

同一份代码的两个名字：srsRAN Project 和 OCUDU 的对比

一句话：OCUDU 就是 srsRAN Project 换了名字继续往前走。两边共享 16,380 个 commit（2021-11 到 2025-12-03）， 之后 srsRAN 只多了 159 个 commit 就归档了，OCUDU 又走了 3,421 个。我们关心的 RLC / PDCP / RRC 这三块， OCUDU 主要是加功能（RRC resume、分段窗口、XnAP），旧 bug 基本原样继承。

这一页回答三个问题：① 两边重叠的是什么；② 不一样的是什么（删了、加了、什么时候）； ③ RLC AM 那个 bug 在每个版本里是怎么改的，我们能学到什么。

状态说明（2026-09-21）：两边的最新代码已经拉下来并做完了代码级对比和历史分析（下面都是）。 Specula 在最新代码上的重跑还没开始：lab box 的根分区被 /tmp/gnb.log（31 GB，root 所有）撑满， Specula 和 agent 都写不了盘。所以本页 Specula 部分用的是已有的两次运行 （srsRAN，9 月 1 日；OCUDU，9 月 17 日）， 再把每个 finding 拿到两边最新代码里逐条人工核对。磁盘腾出来后重跑，结果会更新到这一页。

3 · 一个 bug 的逐版本历史：RLC AM 的两个 timer

机制先讲清楚。RLC AM 靠两个 timer 找回丢掉的 PDU。发送端在某个 PDU 上置 poll 位、记下 POLL_SN、启动 t-PollRetransmit；接收端回一个 STATUS PDU（ACK_SN 加一串 NACK），但两个 STATUS 之间至少要隔 t-StatusProhibit。timer 到期还没收到 STATUS，发送端就重传并再 poll 一次。每个 SDU 有 RETX_COUNT， 到了 maxRetxThreshold 就报 RLF。

这套机制在 srsRAN→OCUDU 的 4 年历史里被改过很多次。下面分两部分： 3.1 整套 poll/STATUS 逻辑在每个版本的行为（用 TLC 逐版本检查）； 3.2 其中两次 Specula 都撞到的那个崩溃（NACK_SN == TX_Next）从出生到今天的完整历史。

3.1 每个版本的 poll / STATUS 行为

做法：把历史上每次修复变成模型里的一个开关（8 个），从 git 每个版本的源码里读出开关的取值，得到 10 个行为区间， 每个区间用 TLC 检查 7 条性质。今天重新对最新 HEAD d0df5e24f 读了一遍，开关取值和 9 月 17 日完全一样，所以下表对最新代码成立。 模型和脚本：ORAN-DOMAIN（models/ocudu_rlc.tla、experiments/ocudu_switches.py、ocudu_run.py）。

① 10 个区间里没有一个是全绿的。每次修一个，旁边还留着一个，或者顺手带进来一个新的。

② 两个 bug 是"优化"带进来的，不是写功能带进来的：0cbb2550b（把 timer 挪到别的 executor）和 ddc309c8b（去掉 malloc）。后者活了 351 天，跟着 24.04、24.10、24.10.1 三个公开 release 发出去了—— 修复 2024-11-07 就进了主线，但 2025-01-09 的补丁版 24.10.1 没带上它。

③ defer 失败锁死（srsRAN 那次 Specula 的 MC-3）从 2023-03-10 活到今天，而它的"孪生兄弟"——MAC buffer-state 通知的同一种写法—— 2026-08-13 已经被 a1491504c 修了。同一个 RLC 模块里，同一种错，只修了一处。

3.2 那个崩溃：NACK_SN == TX_Next

两次 Specula 独立撞到的同一个 bug（srsRAN 那次叫 MC-6，OCUDU 那次叫 MC-5），输入都是同一个：全新的发送实体收到 ACK_SN = 1, NACK_SN = 0 的 STATUS PDU。handle_nack 的范围检查是 TX_Next_Ack ≤ NACK_SN ≤ TX_Next，右边是闭区间，而 TX_Next 是"下一个要发的 SN"，还没发过，窗口里没有这个槽； 下一行就去读 tx_window[nack_sn]。

3.3 我们能学到什么

① bug 不是没人碰，而是被人绕着修了四次。这段代码周围，4 年里有 4 批修复（2023-01、2023-02 三连、2024-02 两连、2026-08 接收端）。 每一批都是看到一个具体的现场症状、修掉那个症状。没有人回头问"tx_window[sn] 的前提到底是什么"。 一条写下来的不变式（访问窗口前 SN 必须存在，Specula 给它起的名字是 WindowAccessRequiresPresence）一次就能盖住全部四批。

② 闭区间是对的，错的是少了一句话。≤ TX_Next 不是笔误：分段发送中的 SDU 就需要它。所以"把 ≤ 改成 <"这种看起来显然的修法反而会打破分段重传。 只读 diff 看不出这一点，要读 2022-08 和 2024-02 这两次提交的意图才知道。理解一个 bug 需要它的历史。

③ 构建策略会悄悄改变 bug 的严重程度。同一个 bug 的表现变了两次，两次都没碰那段 RLC 逻辑：2025-12-05 的 CMake 改动把"assert 退出、日志里有明确一行"变成了"静默读写空槽"；2026-06-26 的窗口容器重构又把它变成了 SIGSEGV。 只盯着协议代码的分析（包括大多数 fuzz 和单测）看不到这种变化；逐版本跑同一个模型 + 同一个复现才能看到"同一个 bug，表现变了"。

④ 改名和换仓库不会修 bug。16,380 个 commit 原封不动搬过去，bug 也一起搬过去。OCUDU 继承的不只是代码，还有 #464 这种"复现不了就关掉"的 issue 历史—— 而旧 issue tracker 归档之后，新项目的人更难搜到它。

⑤ 同类错误只修一处，是最可预测的漏网方式。3.1 的 defer 锁死（修了 MAC 通知那处，没修 t-StatusProhibit 那处）和 3.2 的 has_sn（修了接收端，没修发送端）是同一个模式， 两次都发生在 2026-08-13 同一天的提交里。每一次修复都在告诉你一条性质；把它写成性质，就能自动去查所有兄弟位置。

⑥ 现场报告早于工具 19 个月。#464 在 2024-02 就报了同一个 assert。缺的不是信号，是一个能从"一行 assert 日志"反推出"什么输入能到这里"的手段——这正是模型检查给的： OCUDU 那次的 hunt 配置只探索了 80 个不同状态就给出反例，输入只有一个 STATUS PDU。
