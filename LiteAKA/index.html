第二步的依据 · Basis for step 2

下面每一条都是我们用自己的话写的总结，不是原文。核对的版本：TS 33.501 V18.12.0（2026-07）、TS 33.535 V18.8.0、TS 33.102 V18.0.0、TS 24.501 V18.14.0。
Each item below is our own summary, not spec text. Checked against TS 33.501 V18.12.0 (2026-07), TS 33.535 V18.8.0, TS 33.102 V18.0.0 and TS 24.501 V18.14.0.

KAMF · 一直在用 / always in use

KAMF 由 KSEAF 派生，放在 AMF 和 UE 的 5G NAS 安全上下文里。NAS 密钥、每次进入连接态的 KgNB、切换用的 NH 都从它派生。每次主认证都会换一个新的 KAMF；注销以后这个上下文也可以留着，下次注册接着用。

KAMF is derived from KSEAF and kept by the AMF and the UE in the 5G NAS security context. The NAS keys, a new KgNB for every move to connected mode, and NH for handover are all derived from it. Each primary authentication yields a new KAMF, and the context may be kept after deregistration for the next registration.

TS 33.501 §3.1, §6.2.2.1, §6.8.1.1, Annex A.7–A.10

KNASenc / KNASint · 一直在用 / always in use

NAS SMC 之后，UE 和 AMF 之间的每条 NAS 消息都必须做完整性保护，没有保护的消息不再接受（少数例外列在 TS 24.501 §4.4.4）。加密也会打开，但标准允许选空加密算法 NEA0，所以加密是可选的，完整性不是。

After the NAS SMC, every NAS message between UE and AMF must be integrity protected, and unprotected ones are rejected (the few exceptions are listed in TS 24.501 4.4.4). Ciphering is switched on as well, but the null algorithm NEA0 is allowed, so confidentiality is optional while integrity is not.

TS 33.501 §5.5, §6.4.3, §6.4.4; TS 24.501 §4.4.2.5, §4.4.4, §4.4.5

KgNB → RRC / UP 密钥 · 连接期间一直用 / always in use while connected

UE 从空闲态进入连接态时，AMF 和 UE 用 KAMF 和这次的上行 NAS COUNT 算出新的 KgNB，再派生 RRC 和用户面的密钥。连接期间 RRC 消息必须做完整性保护；RRC 加密、用户面的加密和完整性都是可选的，按策略决定。回到空闲态时 AS 密钥全部删掉，下次连接重新算。进入 RRC_INACTIVE 时只保留一部分。

Each time the UE goes from idle to connected, the AMF and the UE derive a fresh KgNB from KAMF and the uplink NAS COUNT, and from it the RRC and user-plane keys. While connected, RRC messages must be integrity protected; RRC ciphering and user-plane ciphering/integrity are optional and set by policy. On return to idle all AS keys are deleted and re-derived at the next connection; RRC_INACTIVE keeps only part of them.

TS 33.501 §5.3, §6.5, §6.6, §6.8.1.2.2, §6.8.1.2.4, §6.8.2.1.2, Annex A.8, A.9

KAUSF · 一直存着，偶尔用 / stored, used now and then

每次主认证成功后，UE 必须存下最新的 KAUSF。AUSF 存不存由运营商决定，只有在用 SoR、UPU 或 AKMA 时必须存。SoR 和 UPU 用它给归属网络下发的配置算 MAC；AKMA 用它派生 KAKMA，再给每个应用单独派生 KAF。平时的 NAS 和空口消息都不用它。

After each successful primary authentication the UE must store the latest KAUSF; the AUSF may store it (operator choice) and must do so when SoR, UPU or AKMA is used. SoR and UPU use it to compute a MAC over configuration data sent by the home network; AKMA derives KAKMA from it and then a separate KAF for each application. Ordinary NAS and radio traffic never uses it.

TS 33.501 §6.1.1.1, §6.2.2.1, §6.2.2.2, §6.14, §6.15; TS 33.535 §6.1, Annex A.2–A.4

KSEAF · 只在那一刻 / only at that moment

认证成功后，AUSF 从 KAUSF 算出 KSEAF 交给 SEAF。SEAF 马上用它算出 KAMF，然后删掉 KSEAF，也不能转给别的网元。标准里以 KSEAF 为输入的派生只有 KAMF 这一个。注意 UE 侧会把 KSEAF 存着。

After a successful authentication the AUSF derives KSEAF from KAUSF and gives it to the SEAF, which immediately derives KAMF, then deletes KSEAF and never forwards it. KAMF is the only key derived from KSEAF. The UE side, however, does keep KSEAF stored.

TS 33.501 §6.2.2.1, §6.2.2.2, Annex A.6, A.7

Security Mode Command · 只在那一刻 / only at that moment

NAS SMC 是一来一回两条消息，作用是启用一套新的 NAS 安全上下文：主认证之后必须做一次，换算法或换密钥时再做。AS SMC 只在从 RRC 空闲态建立连接（初始上下文建立）时做；从 RRC_INACTIVE 恢复、切换、重建连接都不用 AS SMC。

The NAS SMC is one command/complete exchange that takes a new NAS security context into use. It must follow a primary authentication and is repeated only when algorithms or keys change. The AS SMC is used only at initial context setup from RRC idle; resume from RRC_INACTIVE, handover and re-establishment do not use it.

TS 33.501 §6.7.2, §6.7.4, §6.7.3; TS 24.501 §5.4.2

SUCI · 只在那一刻 / only at that moment

UE 只在三种 NAS 消息里发 SUCI：手上没有 5G-GUTI 时的初始注册；网络来要身份时的 Identity Response；还没拿到 5G-GUTI 就注销时的 De-Registration Request。其余时候都用 5G-GUTI，所以 t1 的再认证一般用不到 SUCI。

The UE sends a SUCI in only three NAS messages: an initial registration when it holds no 5G-GUTI, an Identity Response when the network asks for its identity, and a de-registration before any 5G-GUTI has been assigned. Otherwise it uses the 5G-GUTI, so a later re-authentication normally needs no SUCI.

TS 33.501 §6.12.2, §6.12.3; TS 24.501 §5.5.1.2.2

RAND · AUTN · RES* / XRES* · 只在那一刻 / only at that moment

每次认证，UDM 生成一组向量：RAND、AUTN（= SQN⊕AK ‖ AMF ‖ MAC）、XRES*、KAUSF。USIM 先验 MAC 再查 SQN；手机用 CK‖IK 当 key 算出 RES*。SEAF 比较 HRES* 和 HXRES*，AUSF 比较 RES* 和 XRES*。5G 里网络不能一次要多组向量备用，AUSF 也只临时保存 XRES*。

For each run the UDM produces one vector: RAND, AUTN (= SQN⊕AK ‖ AMF ‖ MAC), XRES* and KAUSF. The USIM checks the MAC and then SQN; the phone computes RES* keyed with CK‖IK. The SEAF compares HRES* with HXRES*, and the AUSF compares RES* with XRES*. In 5G the serving network may not fetch several vectors in advance, and the AUSF keeps XRES* only temporarily.

TS 33.501 §6.1.3.2 (NOTE 1), Annex A.4, A.5; TS 33.102 §6.3.2, §6.3.3

AUTS 重同步 · 只在 SQN 对不上时 / only when SQN is out of sync

MAC 对但 SQN 不在可接受范围内时，USIM 返回 AUTS = (SQNMS ⊕ f5*(RAND)) ‖ MAC-S，其中 MAC-S 用 f1* 算、AMF 取全 0。手机把它放在 Authentication Failure 里发回；UDM 先看自己的 SQN 是否已经在范围内，不在就验 AUTS、把 SQN 对齐，然后发一组新向量重新认证。几种认证失败里只有"同步失败"带 AUTS。

If the MAC is valid but SQN is out of range, the USIM returns AUTS = (SQNMS ⊕ f5*(RAND)) ‖ MAC-S, where MAC-S comes from f1* with AMF set to zero. The phone sends it in an Authentication Failure; the UDM checks whether its own SQN is already in range, and if not verifies AUTS and realigns SQN, then issues a new vector for a fresh run. Of the authentication failure causes, only synch failure carries AUTS.

TS 33.102 §6.3.3, §6.3.5; TS 33.501 §6.1.3.3; TS 24.501 §5.4.1.3.6

认证状态 · 一直在 / always there

这一项不在 3GPP 标准里，是 LiteAKA 自己加的。在 5G 里，"之后的消息确实来自认证过的那一方"靠上面三条一直在用的密钥逐条保护来保证。LiteAKA 去掉了这些密钥，换成一个状态让后续功能来查；这个状态本身不对每条消息做密码学验证。

This item is not in the 3GPP specs; LiteAKA adds it. In 5G, "later messages really come from the authenticated party" is guaranteed by the three always-in-use keys above, protecting message by message. LiteAKA removes those keys and keeps a state that later functions check instead; the state itself does not cryptographically verify each message.
