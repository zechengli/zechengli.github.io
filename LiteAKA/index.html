只认证、不加密：从 5G AKA 里去掉了什么

一句话：LiteAKA 在 5G AKA 里算完 RES* 就停下来：只做双向认证， 后面的密钥派生、Security Mode Command、NAS/PDCP 加密和完整性保护全部去掉，SQN 重同步也一并去掉。

按 srsRAN_4G 里 5G UE 侧的安全代码统计：LiteAKA 保留 16.1%， 去掉的加密相关部分占 79.0%，另外去掉的重同步占 4.9%。统计的口径和方法见本页最后。

1. 5G AKA 在 RES* 之后还做了什么

5G AKA 认证成功以后，还会从 CK、IK 一路往下派生出一整棵密钥树，再用这些密钥保护之后的每一条消息：

 K, OPc, RAND
    │  f1..f5 (Milenage)
    ▼
 MAC, RES, CK, IK, AK
    │
    ├──► RES* = KDF(CK||IK, SN name, RAND, RES)      ← LiteAKA 做到这里为止
    │
    └──► KAUSF ─► KSEAF ─► KAMF ─┬─► KNASenc / KNASint ─► NAS 消息加密 + 完整性
                                 └─► KgNB ─┬─► KRRCenc / KRRCint ─► RRC 信令
                                           └─► KUPenc / KUPint   ─► 用户面数据
                                   （还有 Security Mode Command、切换时的 K*gNB、NH …）

LiteAKA 在 RES* 这里停下。从 KAUSF 往下的整棵树、用这些密钥的三套加密和完整性算法 （SNOW 3G / AES / ZUC），以及把它们用到 NAS 和 PDCP 消息上的代码，全部不需要。

2. 保留什么、去掉什么

部分5G AKALiteAKA原因
Milenage f1（MAC）有保留客户端靠它认证服务器
Milenage f2、f3、f4、f5有保留f2 给出 RES；RES* 需要 CK（f3）和 IK（f4）；AK（f5）用来盖住 SQN。四个值在同一次 f2345 调用里一起算出
RES* / XRES*有保留服务器靠它认证客户端，这也是"5G" AKA 和 4G 的区别
SQN + 窗口检查有保留防重放
重同步（f1*、f5*、AUTS、Authentication Failure）有去掉只有一个 Verifier，SQN 基本不会乱；真乱了就手动重置
密钥树（KAUSF 往下）有去掉不加密，也就不需要会话密钥
加密 / 完整性算法（EEA/EIA 1–3，SNOW 3G，ZUC）有去掉同上
Security Mode Command，NAS / PDCP 的加解密和完整性有去掉同上
HXRES*、AUSF/SEAF/AMF 拆分有去掉只有一个 app，一个 Verifier，不存在 home 和 serving 的区别
SN name有换成常量 "liteaka:demo"只有一个服务

代价：认证完以后没有任何密钥保护后续消息。认证只能证明"这一刻对面是有 K 的人"， 之后的请求可能被别人插进来冒充。这对 demo 没有影响，但如果要实际使用，至少应该把 KAUSF → K_int 这一小段加回来，用来做 HMAC。

4. 统计口径

代码版本：srsRAN_4G，commit 6bcbd9e5b（2026-01-18），lab 机器 ubuntuhooray 上的那份。

范围：UE 侧（srsUE）在 5G SA 下会用到的安全代码，包括 lib/src/common/ 下的 security.cc、liblte_security.cc、s3g.cc、zuc.cc， srsue/src/stack/upper/ 下的 usim.cc、usim_base.cc、nas_5g.cc、nas_base.cc， 以及 lib/src/pdcp/pdcp_entity_base.cc。

怎么数：用脚本找出每个函数的范围，统计其中的非空、非注释行，再按函数手动归类。 没有被列在上表里的函数（比如 NAS 的其他消息处理）不计入分母。

没算进去的：

  • AES 本身：Milenage 和 EEA2/EIA2 都调用 mbedtls 的 AES，这部分在第三方库里，两边都要用。
  • 真 SIM 卡路径 pcsc_usim.cc（1,225 行）：用真卡时 f1–f5 在卡里执行。
  • 只在 4G 使用的函数（k_asme、k_enb、k_nas、k_rrc、k_up 等）、测试用的 XOR 算法、security_md5。
  • liblte_security.cc 里的 liblte_security_generate_res_star：srsRAN 实际调用的是 security.cc 里的版本（已用 grep 确认它在 lib/srsue/srsenb/srsepc 里没有调用者）。liblte_security.cc 里 NR 密钥派生的几个函数是否被调用，我没有逐个确认，所以也没算。这几项如果算进去，"去掉"的比例只会更高。
  • 网络侧（Open5GS 的 UDM/AUSF/AMF）没有统计。

所以 16% / 79% 是在这个口径下的数字，换一个口径（比如把网络侧或者 AES 算进去）结果会不一样。
