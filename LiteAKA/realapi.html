所有 API，和每一个变量从哪来

一共六组接口，按 第 6 页 的顺序排：App ↔ SIM，App ↔ 服务器，服务器 ↔ AUSF， Open5GS 内部（我们不直接调，列出来方便对照），其他 App ↔ LiteAKA App，以及桌面上的登记工具。

所有二进制字段在 JSON 里都是 hex 字符串。最后一节是变量表：每个变量是事先知道的还是代码生成的， 是静态的（每次都一样）还是动态的（每次或者随时间会变）。

1. App ↔ SIM（APDU）

走 Android 的 TelephonyManager.iccOpenLogicalChannel / iccTransmitApduLogicalChannel。 这两个接口平时只有系统和运营商 App 能用，我们靠 root 授予 MODIFY_PHONE_STATE 等权限。

命令字节返回
打开逻辑通道iccOpenLogicalChannel("A0000000871002")（USIM 的 AID）通道号
SELECT00 A4 00 00 02 ‖ 文件号：3F00（MF）→ 7F20（DF_GSM）→ 6F07（EF_IMSI）90 00
READ BINARY00 B0 00 00 099 字节 EF_IMSI → 解出 IMSI 999700000085592
AUTHENTICATE00 88 00 81 22 ‖ 10 ‖ RAND(16) ‖ 10 ‖ AUTN(16) 成功：DB ‖ 08 RES ‖ 10 CK ‖ 10 IK
SQN 不同步：DC ‖ 0E AUTS
MAC 不对：98 62
关闭逻辑通道iccCloseLogicalChannel(通道号)—

代码里 SELECT / READ BINARY 用的是老式 CLA A0，发出去之前统一改成 00（逻辑通道上只认 USIM 的 CLA）。 读 IMSI 和做认证各用一个新通道，原因见第 6 页 A2–A5。

2. App ↔ LiteAKA 服务器（HTTP/1.1 + JSON，端口 8780）

① POST /liteaka/v1/start

请求  { "imsi": "999700000085592" }
200   { "session":   "15e1fb9c…（32 hex）",
        "rand":      "0e0a7e4092aa1e9682060f22b400be19",
        "autn":      "…32 hex…",
        "hxresStar": "…32 hex…",
        "snn":       "5G:mnc070.mcc999.3gppnetwork.org" }
HTTP什么时候
400IMSI 不是数字，或者不是 999 70 开头
403SIM … is not registered with the home network：Open5GS 里没有这个用户
502AUSF 出了别的错

② POST /liteaka/v1/resync

请求  { "session": "…", "auts": "…28 hex（14 字节）…" }
200   和 /start 一样，是一道新题（新的 session）

旧 session 会被删掉。session 不存在或者超过 120 秒：400。

③ POST /liteaka/v1/confirm

请求  { "session": "…", "resStar": "…32 hex…" }
200   { "result": "PASS", "supi": "imsi-999700000085592",
        "authenticatedAt": 1791325528, "expiresAt": 1791411928, "validFor": 86400 }
200   { "result": "FAIL", "supi": "imsi-999700000085592",
        "authenticatedAt": null, "expiresAt": null, "validFor": null }

PASS 和 FAIL 都是 200，看 result。session 只能用一次。expiresAt = authenticatedAt + 24 小时（服务器参数 --state-ttl，默认 86400 秒；设成 0 就是永不过期，返回 null）。

App 只用 validFor：从收到结果那一刻起，按手机自己的时钟算 24 小时。实测这台手机的时钟比服务器快 55 秒（手机关了自动对时），如果直接拿服务器的 expiresAt 和手机时钟比，状态会提前失效。

④ POST /liteaka/v1/abort

请求  { "session": "…" }
200   { "result": "ABORTED" }

SIM 拒绝了题目（MAC 不对，或者出错）时，App 用它告诉服务器这道题作废。

⑤ GET /liteaka/v1/health

200   { "ok": true, "ausf": "http://127.0.0.11:7777", "snn": "5G:mnc070.mcc999.3gppnetwork.org" }

3. 服务器 ↔ AUSF（3GPP SBI，HTTP/2 明文）

这是 TS 29.509 定义的 Nausf_UEAuthentication 服务，Open5GS 原样实现。服务器用 curl --http2-prior-knowledge 调。

⑥ POST /nausf-auth/v1/ue-authentications

请求  { "supiOrSuci": "suci-0-999-70-0000-0-0-0000085592",
        "servingNetworkName": "5G:mnc070.mcc999.3gppnetwork.org",
        "resynchronizationInfo": { "rand": "…", "auts": "…" } }   ← 只有重同步时才带
201   { "authType": "5G_AKA",
        "5gAuthData": { "rand": "…", "autn": "…", "hxresStar": "…" },
        "_links": { "5g-aka": { "href": "http://127.0.0.11:7777/nausf-auth/v1/ue-authentications/1/5g-aka-confirmation" } } }
404   用户不存在

⑦ PUT …/ue-authentications/{authCtxId}/5g-aka-confirmation

请求  { "resStar": "…32 hex…" }
200   { "authResult": "AUTHENTICATION_SUCCESS",   （或 AUTHENTICATION_FAILURE）
        "supi": "imsi-999700000085592",
        "kseaf": "…64 hex…" }                      ← 服务器丢掉，不往下传

4. Open5GS 内部（我们不直接调用）

谁 → 谁接口带什么 / 回什么LiteAKA 需要吗
AUSF → UDMPOST /nudm-ueau/v1/{suci}/security-information/generate-auth-data带 servingNetworkName、ausfInstanceId、（resynchronizationInfo）；回 SUPI 和认证向量：rand、autn、xresStar、kausf要（kausf 不要）
UDM → UDRGET /nudr-dr/v1/subscription-data/{supi}/authentication-data/authentication-subscription回 K（encPermanentKey）、OPc（encOpcKey）、AMF、sequenceNumber.sqn要
UDM → UDRPATCH 同上写回新 SQN（+32，或者重同步后的值）要
AUSF → UDMPOST /nudm-ueau/v1/{supi}/auth-events告诉 UDM 认证结果不要
UDM → UDRPUT /nudr-dr/v1/subscription-data/{supi}/authentication-data/authentication-status把认证状态记进数据库不要
各网元 → NRF/nnrf-disc/v1/nf-instances找 UDM、UDR 的地址（经过 SCP）不要（写死地址即可）

5. 其他 App ↔ LiteAKA App（ContentProvider）

URI        content://com.zecheng.liteaka.state/status
权限       com.zecheng.liteaka.permission.CHECK_STATE   （调用方在 manifest 里声明 uses-permission）
返回一行   authenticated     1 / 0
           supi              "imsi-999700000085592"（没认证时为 null）
           authenticated_at  Unix 秒
           expires_at        Unix 秒（手机时钟），认证后 24 小时（0 = 永不过期）

过了 expires_at，authenticated 自动变成 0，要重新认证。

只读。insert / update / delete 都不做任何事。Android 11 以上，调用方还要在 manifest 里加 <queries><provider android:authorities="com.zecheng.liteaka.state"/></queries>。

6. 桌面登记工具（不对手机开放）

subscribers.py list                          列出所有用户和当前 SQN
subscribers.py add <imsi> <ki> <opc>      登记一张卡（SQN 从 0 开始，第一次认证时自动重同步）
subscribers.py remove <imsi>                 删除（先备份到 server/backup/）
subscribers.py restore <备份.json>            从备份恢复

7. 所有变量

四种标记：

  • 已知：事先配好、写在卡里或数据库里的，不是这次流程算出来的。
  • 生成：流程里由代码算出来或随机产生的。
  • 静态：每次认证都一样。
  • 动态：每次都不一样，或者会随时间变化。

7.1 已知 + 静态（事先配好，不变）

变量长度存在哪经过哪些接口说明
K（Ki）16 BSIM、UDR只在 UDR → UDM 内部传长期密钥，永远不出 SIM，也不出 Open5GS
OPc16 BSIM、UDR同上运营商参数（已经和 K 混合过的 OP）
IMSI / SUPI15 位SIM（EF_IMSI）、UDRAPDU、/start、SUCI 里999700000085592；SUPI 就是前面加上 imsi-
AMF2 BUDR在 AUTN 中间8000（separation bit = 1，表示 5G / EPS）
MCC、MNC3 + 2 位服务器代码、Open5GS 配置—999、70
USIM AID7 BApp 代码打开逻辑通道A0000000871002
文件号2 BApp 代码SELECT3F00、7F20、6F07
服务器地址、AUSF 地址—App 界面 / 服务器代码—10.168.1.39:8780、127.0.0.11:7777

7.2 生成 + 静态（每次算出来都一样）

变量长度谁算的经过哪些接口怎么算
SUCI字符串服务器⑥ supiOrSucisuci-0-999-70-0000-0-0-<MSIN>：null scheme，IMSI 明文。用了加密 scheme 才会每次不同
SN name字符串服务器① 返回的 snn、⑥ servingNetworkName5G:mnc070.mcc999.3gppnetwork.org，由 MCC / MNC 拼出来

7.3 已知 + 动态（存着的状态，会变）

变量长度存在哪什么时候变
SQN（网络侧）6 BUDR（MongoDB 里的 security.sqn）每次出题 +32；重同步时改成 SQNMS + 33
SQNMS（卡里）6 BSIM 内部每次认证成功后更新成这次的 SQN。读不出来，只能从 AUTS 里间接看到
认证状态—App 的 SharedPreferences认证成功时写入 SUPI、认证时间、过期时间；失败或点"Clear"时清掉；24 小时后自动失效

7.4 生成 + 动态（每次认证都是新的）

变量长度谁生成经过哪些接口怎么来的LiteAKA 需要吗
RAND16 BUDM⑥ → ① → APDU随机数要
AK6 BUDM、SIM 各算一次不传f5(K, RAND)，用来盖住 SQN要
MAC8 BUDM在 AUTN 里f1(K, RAND, SQN, AMF)要
AUTN16 BUDM⑥ → ① → APDU(SQN ⊕ AK) ‖ AMF ‖ MAC要
XRES / RES8 BUDM / SIMRES：APDU 返回f2(K, RAND)要
CK16 BUDM / SIMAPDU 返回，App 用完清零f3(K, RAND)只用来算 RES*
IK16 BUDM / SIM同上f4(K, RAND)只用来算 RES*
XRES* / RES*16 BUDM / AppRES*：③ → ⑦KDF(CK‖IK, SN name, RAND, RES) 的低 128 位要（判分就靠它）
HXRES*16 BAUSF⑥ → ①SHA-256(RAND ‖ XRES*) 的低 128 位不要（App 只拿来自检）
KAUSF32 BUDMUDM → AUSF 内部KDF(CK‖IK, SN name, SQN⊕AK)不要
KSEAF32 BAUSF⑦ 返回，服务器丢掉KDF(KAUSF, SN name)不要
authCtxId / 确认链接—AUSF⑥ 返回的 _linksAUSF 内部编号要
session16 B服务器① ② ③ ④随机 UUID，120 秒过期，只能用一次要
authResult—AUSF⑦ 返回 → ③ 的 resultRES* == XRES*要
authenticatedAt—服务器③ 返回成功时的 Unix 时间要
expiresAt / validFor—服务器③ 返回expiresAt = authenticatedAt + 24 小时；validFor = 86400（--state-ttl）。App 只用 validFor，按手机时钟计时要

7.5 只在重同步时出现（生成 + 动态）

变量长度谁生成经过哪些接口怎么来的
AK*6 BSIM、UDM不传f5*(K, RAND)
MAC-S8 BSIM在 AUTS 里f1*(K, RAND, SQNMS, AMF = 0000)
AUTS14 BSIMAPDU 返回 → ② → ⑥ resynchronizationInfo(SQNMS ⊕ AK*) ‖ MAC-S

一句话总结：事先要知道的只有 K、OPc、IMSI、AMF 和 PLMN；每次认证真正新产生、并且 LiteAKA 用得上的， 是 RAND、AUTN、RES*（和它在网络侧的对应 XRES*），以及一个会往前走的 SQN。CK、IK 只是算 RES* 的中间值； KAUSF、KSEAF、HXRES* 是 Open5GS 顺手算出来、LiteAKA 用不上的。
