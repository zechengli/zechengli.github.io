只做认证，用到了 Open5GS 的哪些代码

在手机上跑通的版本（2026-10-06）： 网络侧直接用 Open5GS v2.8.0，手机里插的是真 SIM 卡（sysmoISIM-SJA2，IMSI 999700000085592）， 中间一个很小的 Python 服务器只负责转发。没有基站，没有 B210，srsRAN 一行都没用到。

结论先说：一次认证只会走到 Open5GS 的 AUSF、UDM、UDR 三个网元（另外 NRF、SCP 负责它们之间找人和转发）。 其余 12 个网元一个都没碰。真正和认证有关的算法和数据库代码，加起来大约 600 行。

这条路径是从配置和源码一起确认的：/etc/open5gs/ausf.yaml 里 AUSF 的 client 指向 SCP（127.0.0.200:7777）， UDM 和 UDR 也是一样经 SCP 转发。

4. 只做认证，最少需要什么

必须留下的只有这几样：

  • Milenage（f1、f2345）：生成 AUTN 和 XRES，291 行
  • XRES* 的 KDF：77 行
  • SQN 的读、加、写回，以及用 AUTS 重同步：数据库 200 行 + ogs_auc_sqn 25 行
  • 比较 RES* 和 XRES*：AUSF 里一个 memcmp

加起来大约 600 行。其余的代码，要么是把这几件事拆到三个网元里、再用 HTTP/2 + NRF + SCP 连起来的"管道"， 要么是为了认证之后的加密。

在认证路径上、但 LiteAKA 可以去掉的：

  • KAUSF、KSEAF：Open5GS 每次都会算，然后把 KSEAF 交给调用方，留给 AMF 去派生 NAS 密钥。我们的服务器收到后直接丢掉。
  • HXRES*：它是给漫游时的拜访网络（SEAF）先做一遍预检查用的。LiteAKA 只有一个网络，没有拜访网络。手机上目前拿它做一次本地自检，去掉也不影响结果。
  • auth-events / authentication-status：只是记账，认证成功后告诉 UDM、写进 UDR，不影响这次认证的结果。
  • SUCI 解密（ECIES）：我们发的是 null-scheme 的 SUCI，IMSI 明文在里面，所以这 2,400 行用不到。代价是 IMSI 在手机和服务器之间是明文。
  • NRF、SCP：只是用来找地址、转发。如果把 AUSF、UDM、UDR 合成一个程序，它们和三个网元之间的 HTTP/2 接口都可以去掉。

SQN 重同步保留了，而且真的用上了： 把 SIM A 从数据库删掉、重新加进去以后，数据库里的 SQN 从 0 开始，比卡里的小，卡拒绝了第一次 challenge 并返回 AUTS， Open5GS 用 ogs_auc_sqn 重同步以后第二次就通过了。没有这一段，每次重新登记 SIM 都要手动去改数据库里的 SQN。

5. 统计口径

  • Open5GS v2.8.0，git clone --branch v2.8.0，和这台机器上装的 open5gs 2.8.0~jammy5 同一个版本。
  • 网元行数：src/<网元>/ 下 .c + .h 的总行数，包括注释和空行。
  • 库的行数不含自动生成的代码：lib/sbi/openapi（540,278 行）和 lib/asn1c（731,637 行）。
  • 函数行数：从函数定义那一行到下一个函数定义之前，包括函数之间的空行。
  • "执行到"是按源码调用关系和这次实机的 SBI 请求判断的，没有在 Open5GS 里加覆盖率统计。
