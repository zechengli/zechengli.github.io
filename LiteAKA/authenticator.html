与 MS Authenticator 的对比

老板的问题："something similar to MS Authenticator but using AKA — what's the flow?"

左边是 Microsoft Authenticator 实际怎么做，按微软官方文档核对过，没查到的地方标 未核实。 右边是 LiteAKA 基础版：把左边"证明是你本人"那一步从 App 自己生成的密钥换成 SIM 卡里的 AKA。 右边标 已跑通 的是软 SIM 原型里实际跑过的；标 设计 的还没有实现。

Microsoft Authenticator

角色

浏览器（用户在网站登录）· Authenticator App（手机）· Entra ID（微软的身份服务，也是最后给网站发 token 的人）。

信任根：微软的原话是"绑在这台手机上的用户凭据"（key-based，类比 Windows Hello for Business），用 PIN 或生物识别解锁；手机还要在每个要登录的租户里注册过。一台手机可以给多个账号分别开通，是不是每个账号一把密钥、密钥什么时候生成，微软没写 未核实。私钥存在哪里（Secure Enclave / Keystore / TEE）也没写 未核实；不过微软的 amr 表给手机登录标的是 swk（RFC 8176：软件保护的密钥），给 Windows Hello 标的是 hwk（硬件密钥），说明微软自己也把它当软件密钥。

注册（一次）

  1. 用户登录 mysignins.microsoft.com/security-info，点"添加登录方法 → Microsoft Authenticator"。
  2. 页面显示二维码。微软说扫码是为了确认"手机确实在你手里"。二维码的格式微软没公开，但它给的替代方式是"手动输入一个码和一个 URL"，数据文档里把这一步叫 activation；这个码是不是一次性密钥、有效期多长，没写 未核实。
  3. App 扫码，账号加进 App（这一步只拿到 MFA 推送）。要用无密码登录，用户还要在 App 里点这个账号 →"Set up Passwordless sign-in requests"，前提是管理员允许、手机有锁屏 PIN / 生物识别；这一步会做设备注册，手机成为 Entra registered 设备。微软只说这是"基于密钥的用户凭据"、登录时 Entra 做公私钥校验，密钥什么时候生成、公钥什么时候传给 Entra 没写 未核实。微软的数据存留文档写了服务端保存 Authenticator 的 "device token" 和它的变更（保留 90 天），但没说这就是 APNS / FCM 的推送令牌、也没说是在哪一步上传的 未核实。
  4. 最后必须批准一次测试推送，并输入屏幕上的数字。

登录（每次，无密码手机登录）

  1. 用户在网站输入用户名。
  2. Entra 识别出这个账号有强凭据，启动 Strong Credential 流程。
  3. Entra 通过 APNS（iOS）/ FCM（Android）推送到 App。推送里可以显示发起登录的应用名（Entra 里注册的应用名，不一定是网站域名）和按 IP 推的大概位置；这两项默认由微软管理，目前定为关，管理员可以开。
  4. 用户打开 App。
  5. App 向 Entra 取一个"在场证明"挑战和 nonce。
  6. 用户输入网页上的数字，用生物识别或 PIN 解锁设备私钥。
  7. App 用私钥签 nonce，发回 Entra。
  8. Entra 用注册时存的公钥验签，给网站发 token。

微软的 8 步协议图里没有数字匹配这一步；数字匹配是另一页讲的用户体验：网页出现一个数字，用户在 App 里输入 → Approve → PIN / 生物识别。数字在哪一步生成，微软没写。第一次用时用户还要先选 "Approve a request on my Authenticator app"。

无密码手机登录从一开始就带数字匹配，用户不能关。2023-05-08 起微软把 MFA 推送（原来点 Approve / Deny 那种）也全部改成数字匹配，原因是防"MFA 疲劳轰炸"；这个日期来自微软博客和文档旧版本，现在的 Learn 页面已不写日期。例外：同一台手机上登录 Teams / Outlook 等微软 App 时只回答 Yes / No，不输数字；NPS 扩展、没打补丁的 AD FS、旧的 MFA Server 和手表不走数字匹配。数字是两位：Learn 文档页没写位数，是微软 Entra 博客《Defend your users from MFA fatigue attacks》（2022-09-28）写的 two-digit code。

网站拿到什么

标准的 OIDC ID token（签名的 JWT）：iss、aud、nonce、每个网站不同的 sub。 用了什么方法写在 amr 里。按微软的表，无密码手机登录发 ["swk","rsa","mfa"]；密码 + Authenticator 推送是 ["rsa","ngcmfa","mfa"] 加 pwd。rsa 表示"用一把 RSA 密钥证明过"，Authenticator 是其中一种（证书认证也会发 rsa）；手机登录特有的标记是 swk。amr 在 v2.0 token 里要网站自己申请（optional claim）才有，v1.0 默认带。

安全等级（微软自己的分类）

手机登录算 Passwordless MFA，不算抗钓鱼（Phishing-resistant）。抗钓鱼那一档只有 passkey（FIDO2）等。

LiteAKA 基础版

角色

浏览器 · LiteAKA App + SIM 卡（手机）· Verifier（我们自己写的服务器，扮演运营商：持有 K，出题、判分，最后给网站发 token）。

信任根：运营商写在 SIM 卡里的 K，拿不出来。手机上另外有一把设备密钥，注册时由那次 AKA 给它作保。

注册（一次）

  1. 用户在网站登录后点"添加 LiteAKA"。设计
  2. 服务器显示二维码：服务器地址 + 一次性注册码，5 分钟有效。设计
  3. App 扫码；生成设备密钥（现在是文件，目标是 Android Keystore）；读出 IMSI。设计
  4. App 发 /enroll/start：注册码、IMSI、设备公钥。设计
  5. Verifier 用 K 出题：RAND、AUTN。RES* 的 P0 里绑上注册号和设备公钥的哈希。已跑通
  6. App 把 RAND、AUTN 交给 SIM：MAC 不对就中止（对面没有 K）；SQN 不同步就回 AUTS 重同步，再来一次。已跑通
  7. App 算出 RES*，连同设备签名发回；然后把 CK、IK 从内存清掉。已跑通
  8. Verifier 比对 RES* 和 XRES*，验签；存 {账号, SUPI, 设备公钥} 和一个认证状态 {AKA 时间, 到期时间}。已跑通
  9. 做一次测试登录，带数字匹配。设计

登录（每次）

  1. 网站把用户跳转到 Verifier 的 /authorize（标准 OIDC）。设计
  2. Verifier 建一笔交易：交易号、数字 n、nonce、网站名和大概位置，120 秒有效、只能用一次；网页显示 n。设计
  3. 推送到 App，推送里只放交易号。设计
  4. App 用设备密钥签名，去拉这笔交易的详情；如果这次要跑 AKA，详情里带着 RAND、AUTN。已跑通（签名拉取就是原型里的 /challenge + /check）
  5. App 显示"要登录 某某网站 吗？"，用户输入数字，点批准（也可以拒绝），生物识别解锁设备密钥。设计
  6. 认证状态还有效：只用设备密钥签（交易号, n, nonce）。状态过期了，或者网站要求最新的 AKA：SIM 再做一次题，RES* 的 P0 绑上交易号、n 和设备公钥哈希。已跑通（两条路都在原型里，只是还没有数字 n）
  7. App 发回签名（跑了 AKA 就连 RES* 一起）。已跑通
  8. Verifier 检查交易没过期没用过、数字对、签名对、状态没被撤销；通过后发 code，网站换成 ID token。设计

AKA 什么时候跑：注册时一定跑；登录时只在状态过期、网站要求、或触发风险规则（数字输错、新地点、疑似换卡）时跑；平时登录不跑。 有效期 TTL 是一个参数：TTL = 0 就是每次登录都跑 AKA，TTL = 24 小时就是现在实机版的做法。

网站拿到什么

和左边一样是 OIDC ID token：每个网站不同的 sub（绝不放 SUPI），acr 写明这次是 liteaka:state（查状态）还是 liteaka:aka（新跑了 AKA），再加 aka_time。设计

安全等级

和左边一样属于 Passwordless MFA，同样不抗钓鱼：实时的中间人钓鱼页会把真数字转给受害者看。AKA 改变不了这一点。

两边最关键的区别

Microsoft AuthenticatorLiteAKA
信任从哪来App 自己生成的设备密钥；靠"扫码时你刚通过 MFA 登录（已有 MFA 方法的用户 10 分钟内要做一次）"加设备注册来认它运营商写在 SIM 里的 K，注册时给设备密钥作保，之后随时可以要求再验一次。所以能发现换卡（SIM swap），微软看不到 SIM
手机能不能验服务器微软没写，只能推断是靠 TLS 未核实；微软自己只说手机登录不属于"方法和登录界面有交互"的抗钓鱼那一档能：SIM 只回答用 K 出的题，假服务器什么也拿不到（软 SIM 测过，e2e_test.sh 第 3 项）
谁来运营微软运营 Entra ID；推送要经 Apple APNS / Google FCM 转一手（中国大陆 Android 推送不通）Verifier 必须是持有 K 的一方，也就是运营商。实验室里我们自己扮演；接 AT&T 的话现实中只能拿到号码验证（CAMARA / TS.43），拿不到 AKA 的值
离线备用有 TOTP 验证码，但要管理员开 "Allow use of Microsoft Authenticator OTP"，而且是密码 + 验证码：离线时退回有密码的登录没有

一句要老实说的话：RES* 是手机软件（ME）用 CK‖IK 算的，不是 SIM 卡里面算的（TS 33.501 §6.1.3.2.0）。所以"SIM 给设备密钥作保"严格说是"算 RES* 的那段代码在那一刻能访问 SIM"。能碰到 SIM 的代码（root、运营商特权的 App、读卡器）都能绑自己的密钥。

已有的类似东西

  • GBA Push（TS 33.223）：服务器推送、SIM 回答 AKA 题，是最接近的标准方案。
  • AKMA（TS 33.535）和它的后续研究：AKMA+（USENIX Security 2025，作者里有 Purdue 的 Bertino）、E2E-AKMA（USENIX Security 2026）。
  • 商用号码验证：AT&T、T-Mobile、Verizon 通过 Aduna 上线了 CAMARA Number Verification；Android 有 TS.43 的号码验证 API。
  • 没有搜到"每次登录推送一次 AKA，并把设备公钥绑进 AKA 结果"的工作。只说明没搜到，不能证明不存在。
