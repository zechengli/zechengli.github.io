Title: PDCP TX: reset() leaves the discard timer running on UM re-establishment (new SDU discarded early)
Labels (suggested): bug, pdcp

---

## Summary

For SRBs and UM DRBs, `reestablish()` calls `reset()`, which clears the state and the TX window but, unlike `stop()` and `suspend()`, does not stop `discard_timer`:

```cpp
// lib/pdcp/pdcp_entity_tx.cpp:965-970
void pdcp_entity_tx::reset()
{
  st = {0, 0, 0, 0, 0};
  tx_window.clear();                                   // <- no discard_timer.stop()
  logger.log_debug("Entity was reset. {}", st);
}
```

`handle_sdu()` only arms the timer when it is not running (`:307`). The first SDU after the re-establishment (COUNT 0 again) therefore gets no deadline of its own. When the old timer fires, `discard_callback()` discards it. The comment at the call site (`:466-470`) says `reset()` is meant to avoid "multiple discard timers associated with the with the same COUNT". 6949f051ef fixed the same omission in `stop()`.

## Trigger

1. UM DRB, discardTimer 10 ms. An SDU is sent at t=0.
2. `reestablish()` at t=3. A new SDU is sent at t=3 (its deadline should be t=13).
3. At t=10, the old timer fires and the new SDU is discarded.

In practice: handover or RRC re-establishment of a UE with traffic on a UM DRB. In the default QoS table, 5QI 1 is UM with a 100 ms discardTimer.

## Impact

After each UM re-establishment, the SDUs sent before the old deadline can be discarded up to one discardTimer early, possibly while they are still queued at RLC. If no SDU is pending, the stale expiry only logs an error. One DRB, no crash.

## Suggested fix

Add `if (cfg.discard_timer.has_value()) { discard_timer.stop(); }` to `reset()`, as in `stop()` and `suspend()`. With this change all 19 `pdcp_tx_reestablish_test` tests pass, and so do the other PDCP tests.

## Related

- 6949f051ef ("pdcp: make sure discard timer is stopped on stop()"): the same fix, applied only to `stop()`.
- #607 / !1106 / !1250: these fix the PDCP TX crypto path (`apply_reordering()`, `crypto_reordering_timeout()`). !1106 mentions re-establishment, but none of them changes `reset()` or the discard timer.
