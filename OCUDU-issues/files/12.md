Title: PDCP RX: PDUs buffered during a CU-UP key change are processed with the new keys, is this intended?
Labels (suggested): question, pdcp

---

## Summary

When a Bearer Context Modification carries `securityInformation`, the CU-UP routine calls `begin_pdcp_buffering()`, then `set_security_config()` (which calls `configure_security()` on every DRB), then `end_pdcp_buffering()` (`cu_up_bearer_context_modification_routine.cpp:68`, `:75`, `:82`/`:119`). `pdcp_entity_rx` stores buffered PDUs without recording which keys were active at the time, and `end_buffering()` replays them through `handle_pdu()` with the **new** security engines:

```cpp
// lib/pdcp/pdcp_entity_rx.cpp:144-148, end_buffering()
  while (not pdu_buffer.empty()) {
    byte_buffer_chain buf = std::move(pdu_buffer.top());
    pdu_buffer.pop();
    handle_pdu(std::move(buf));              // <- always processed with the new keys
  }
```

Is it intended that every buffered PDU is assumed to be protected with the new keys? For intra-CU handover, the modification is sent after RRCReconfigurationComplete (`intra_cu_handover_target_routine.cpp:51`, `:76-89`), so most buffered PDUs are probably new-key PDUs. However, UL PDUs that the UE protected before switching, and that are still in flight or delivered by the lower layers, can arrive in the same window. TS 38.323 5.1.2 has those processed before the new keys are applied. With UP integrity on, such a PDU causes an integrity failure and a bearer-context release request. With integrity off, it is deciphered with the wrong keystream and delivered upward.

## Trigger

1. DRB with ciphering on and security configuration A. `begin_buffering()`.
2. A PDU protected with configuration A arrives and is buffered.
3. `configure_security(B)`, then `end_buffering()`: the PDU is processed with B.

The tests model the key change as an algorithm change with the same keys (NIA1/NEA1 to NIA2/NEA2), because the checked-in vectors use the default keys. For the entity, both cases replace the security engines. In practice: E1AP Bearer Context Modifications with `securityInformation` (handover, re-establishment, key refresh) while UL traffic is flowing. I have not measured how often old-key PDUs arrive in this window.

## Reproduced

On `dev` 8fe05a213f, Debug and Release builds, driving `pdcp_entity_rx` in the routine's call order. The tests assert the behaviour I would expect *if* the buffered PDU used the old keys, and they fail on current code:

## Impact

If old-key PDUs do arrive in this window: with integrity on, the UE's bearer context is released; with integrity off, corrupted UL packets are forwarded to the core. This happens per UE, once per key change.

## Suggested fix

If this case should be handled: tag each buffered PDU with the security generation that was active when it arrived, and in `end_buffering()` process it with the matching engines, or drop it. If "new keys for everything buffered" is intended, these tests are not meant to be merged.
