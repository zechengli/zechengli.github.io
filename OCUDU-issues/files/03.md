Title: PDCP TX: full UE DL queue returns last crypto token on crypto thread (data race, off-strand resume)
Labels (suggested): bug, pdcp

---

## Summary

`pdcp_crypto_token_manager` signals "all crypto tasks finished" through `pending_crypto`, a `manual_event_flag`. That event is not thread-safe: `flush()` changes a plain `void*` state with `std::exchange` and resumes awaiters inline (`include/ocudu/support/async/detail/event_impl.h:62-78`). This is fine as long as the last token is returned on the UE DL executor, which is the normal path.

When `apply_security()` cannot hand the PDU back because the UE DL queue is full, the continuation, and the token in it, is destroyed on the crypto thread:

```cpp
// lib/pdcp/pdcp_entity_tx.cpp:774-779, apply_security()  (runs on crypto_executor)
  auto fn = [this, pdu_info = std::move(pdu_info)]() mutable { apply_reordering(std::move(pdu_info)); };
  if (not ue_dl_executor.execute(std::move(fn))) {       // <- fn and its token are destroyed here, on the crypto thread
    ...
      logger.log_debug("Dropped PDU, UE executor queue is full. count={}", tx_count);
```

If that is the last token, `return_token()` (`lib/pdcp/pdcp_crypto_token.h:30-43`) calls `pending_crypto.set()` on the crypto thread while the owner awaits the event on the UE strand: `ue_context::stop()` via `await_crypto_tx_all_drbs()` (`lib/cu_up/pdu_session_manager_impl.cpp:861`), or the suspend and security-key-change paths of `cu_up_bearer_context_modification_routine` (`:38-40`, `:69-71`). The result is a data race on the event state, and the teardown or rekey coroutine resuming on a crypto-pool thread and touching UE state off the strand. The `handle_failure` lambda (`pdcp_entity_tx.cpp:729-757`) has the same pattern.

## Trigger

1. A PDCP TX entity with a multi-threaded crypto executor and a bounded UE DL executor whose queue is full.
2. Push SDUs so that crypto tasks are in flight.
3. On the owner: call `notify_pdu_processing_stopped()`, then `CORO_AWAIT(crypto_awaitable())`.

In practice: a UE release, E1AP bearer-context suspend or security-key change while that UE's DL executor queue (`cu_up_dl_ue_executor_queue_size`, default 8192) is full under DL overload and SDUs are still being ciphered.

## Impact

One UE: its teardown or security-key-change coroutine runs on a crypto worker concurrently with the UE strand until its next executor hop, which is undefined behaviour. It needs DL overload during one of those control procedures.

## Suggested fix

Give `pdcp_crypto_token_manager` the owner executor and have `return_token()` dispatch `pending_crypto.set()` there when `prev_token == 0` (with a retry so the signal cannot be lost).
