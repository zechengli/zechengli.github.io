Title: RLC AM RX: one failed defer in get_status_pdu() blocks STATUS reports on the bearer for good
Labels (suggested): bug, rlc

---

## Summary

`rlc_rx_am_entity::get_status_pdu()` defers the start of t-StatusProhibit to the UE executor, but sets `status_prohibit_timer_is_running` even when that `defer()` fails:

```cpp
// lib/rlc/rlc_rx_am_entity.cpp:657-660
if (not ue_executor.defer([&]() { status_prohibit_timer.run(); })) {
  logger.log_error("Unable to start prohibit timer");
}
status_prohibit_timer_is_running.store(true, std::memory_order_relaxed);   // <- set even if defer failed
```

The only place that clears the flag is `on_expired_status_prohibit_timer()` (`:693`), and that never runs because the timer was never started. `status_report_required()` (`:671`) is `do_status && !status_prohibit_timer_is_running`, so it stays false for the rest of the bearer's life and the TX side never sends another STATUS PDU, even when the peer polls.

## Trigger

1. AM bearer with `t_status_prohibit > 0`.
2. The UE executor queue is full at the moment MAC pulls a STATUS PDU (`get_status_pdu()`), so the defer fails.
3. The queue drains; the peer later sends a PDU with the poll bit set.

In practice: a short burst that fills the UE control strand queue (`ctrl_queue_size`) while a STATUS PDU is being built. The test uses a `manual_task_worker` with a single slot in non-blocking mode to make the defer fail.

## Impact

After a single failed defer, that bearer never sends a STATUS PDU again. The peer's TX window stalls and it eventually reaches max retransmissions (RLF) or the bearer stays stuck. The overload that caused it can be gone by then; only one error log line is left.

## Suggested fix

Set `status_prohibit_timer_is_running` only when the defer succeeded, so the next `get_status_pdu()` tries again. With that change the new test and the rest of `rlc_rx_am_test` pass.
