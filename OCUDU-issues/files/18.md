Title: RLC UM RX: t-Reassembly stop check ignores SN wrap-around (timer keeps running after gap is filled)
Labels (suggested): bug, rlc

---

## Summary

In `rlc_rx_um_entity::handle_pdu()` the "stop t-Reassembly" conditions compare raw SNs, while the rest of the function uses `rx_mod_base()`:

```cpp
// lib/rlc/rlc_rx_um_entity.cpp:224 and :230
if (st.rx_timer_trigger <= st.rx_next_reassembly) {          // <- no rx_mod_base()
...
if (st.rx_next_highest == st.rx_next_reassembly + 1) {        // <- no modulus
```

After the SN space wraps, e.g. RX_Timer_Trigger = 63 and RX_Next_Reassembly = 5 with 6-bit SNs, `63 <= 5` is false, so t-Reassembly is not stopped although the gap that started it has been filled (TS 38.322 5.2.2.2.3: "if RX_Timer_Trigger <= RX_Next_Reassembly ... stop and reset t-Reassembly").

## Trigger

1. 6-bit UM bearer; SN 61 is lost, SN 62 and 63 arrive → t-Reassembly starts, RX_Timer_Trigger = 63.
2. SN 0..4 of the next cycle arrive.
3. SN 61 arrives late → RX_Next_Reassembly = RX_Next_Highest = 5, but t-Reassembly keeps running.

In practice: any reordering or late arrival around the SN wrap point, which on 6-bit UM bearers happens every 64 SDUs.

## Impact

t-Reassembly runs spuriously on that bearer. By code reading, a new gap during that time does not get its own timer start, so its loss is detected later than configured; I verified only that the timer keeps running, not any data loss.

## Suggested fix

Use `rx_mod_base()` on both sides of both comparisons, as the start conditions a few lines below already do. With that change the new test and the rest of `rlc_um_test` pass.
