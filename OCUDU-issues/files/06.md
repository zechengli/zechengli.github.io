Title: PDCP TX: discard timer restarted with 0 ms after expiry (next SDUs discarded before their deadline)
Labels (suggested): bug, pdcp

---

## Summary

When the discard timer expires, `discard_callback()` discards the oldest SDU(s) and restarts the timer for the next SDU. It computes the new timeout from the arrival tick of the SDU that **has just expired** instead of the next SDU's own tick. That deadline is already in the past, so `compute_next_discard_timeout()` clamps it to `now` and the timer is always restarted with 0 ms:

```cpp
// lib/pdcp/pdcp_entity_tx.cpp:1432, discard_callback()
std::chrono::milliseconds new_timeout = compute_next_discard_timeout(oldest_timepoint);   // <- tick of the expired SDU
```

The next SDU is therefore discarded on the next tick, and this repeats until a transmit/delivery notification restarts the timer through `stop_discard_timer()`, which passes the correct tick (`:1358-1359`). The line came in with !994 (bf369af9c8); before that, the callback re-armed with the distance to the next SDU's deadline.

## Trigger

1. AM DRB, discardTimer 10 ms. SDU A arrives at t=0, SDU B at t=5 (B's deadline is t=15).
2. No delivery notification arrives.
3. At t=10 A is discarded and the timer is restarted with `new_timeout=0ms`. B is discarded at t=11.

In practice: any DRB with a finite discardTimer whose timer actually expires while more SDUs are queued, i.e. a congested or stalled bearer.

## Reproduced

On `dev` 8fe05a213f, Debug and Release builds. The test below asserts the correct behaviour and fails on current code:

## Impact

After an expiry, queued DL SDUs are discarded up to one discardTimer before their configured deadline, and the callback runs on every tick while they are queued. One DRB, no crash.

## Suggested fix

Pass the next SDU's own tick, as `stop_discard_timer()` does: `compute_next_discard_timeout(window_elem.sdu_info.tick_point_of_arrival.value())`. With this change the test passes and the existing PDCP tests still pass.

## Related

- !994 (fixes #553): introduced this line. The `std::max(..., now)` clamp it added is still needed.
- #666 (open): may be related, since the per-tick callback work would run on `ue_dl_exec` and disappear with discard disabled. Not verified.
