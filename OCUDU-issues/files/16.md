Title: RLC UM RX: t-Reassembly checks the gap of RX_Next_Highest instead of RX_Next_Reassembly (SDU lost)
Labels (suggested): bug, rlc

---

## Summary

When `RX_Next_Highest = RX_Next_Reassembly + 1`, TS 38.322 5.2.2.2.3/5.2.2.2.4 start, stop or restart t-Reassembly depending on whether the SDU with **SN = RX_Next_Reassembly** has a missing byte segment. The code comments quote this, but all three checks in `rlc_rx_um_entity.cpp` look at the SDU with SN = RX_Next_Highest:

```cpp
// lib/rlc/rlc_rx_um_entity.cpp:256-257 (same at :231 and :496)
if (rx_mod_base(st.rx_next_highest) == rx_mod_base(st.rx_next_reassembly + 1)) {
  if (rx_window.has_sn(st.rx_next_highest) && rx_window[st.rx_next_highest].has_gap) {   // <- should be rx_next_reassembly
```

SN = RX_Next_Highest has normally not been received yet, so the check reads as "no gap". If only a later segment of SN = RX_Next_Reassembly has arrived, t-Reassembly is not started. It starts one event later with an RX_Timer_Trigger one SN too high, and its expiry then also discards the next SDU, which had only just started arriving. The AM entity does this correctly with `rx_window[st.rx_next]` (`rlc_rx_am_entity.cpp:286`).

## Trigger

1. UM RX receives the last segment of SN 0 (spec: start t-Reassembly, RX_Timer_Trigger = 1; code: nothing).
2. It receives the first segment of SN 1 (code: start t-Reassembly, RX_Timer_Trigger = 2).
3. t-Reassembly expires: SN 0 **and** SN 1 are discarded.
4. The first segment of SN 0 and the last segment of SN 1 arrive; both are dropped.

In practice: ordinary HARQ reordering of segments across two consecutive segmented UM SDUs; no PDU is lost on the air.

## Impact

One UM SDU is silently lost per occurrence although all its bytes were received. Affects one bearer (UM is typically used for delay-sensitive DRBs such as voice).

## Suggested fix

Check `rx_window.has_sn(st.rx_next_reassembly)` / `rx_window[st.rx_next_reassembly].has_gap` at all three sites. With that change the new test and the rest of `rlc_um_test` pass.
