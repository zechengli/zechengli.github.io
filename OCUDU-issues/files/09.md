Title: PDCP RX: PDU received before t-Reordering expiry is dropped while its crypto is running (UL SDU loss)
Labels (suggested): bug, pdcp

---

## Summary

`handle_data_pdu()` posts a received PDU to the crypto executor (`pdcp_entity_rx.cpp:375`). The COUNT is only inserted into `rx_window` later, in `apply_reordering()`. Until then, a COUNT that has already been received looks lost to `handle_t_reordering_expire()`, which only looks at `rx_window`. If t-Reordering expires in that interval, `RX_DELIV` is moved past the COUNT. When its crypto then completes successfully, the PDU is dropped as stale:

```cpp
// lib/pdcp/pdcp_entity_rx.cpp:466-473, apply_reordering()
  if (rcvd_count < st.rx_deliv) {
    ... "Out-of-order after timeout, duplicate or count wrap-around. count={} {}" ...
    return; // Invalid count, drop.        // <- a verified PDU that arrived before the expiry
  }
```

In TS 38.323 5.2.2.1, receiving a PDU and updating the window happen in one step, so a PDU received before t-Reordering expires is delivered by the expiry procedure in 5.2.2.2.

## Trigger

1. AM DRB, t-Reordering 10 ms. COUNT 1 is received and processed, and t-Reordering starts.
2. 9 ms later, COUNT 0 is received and its crypto task is queued.
3. t-Reordering expires before that crypto task runs. `RX_DELIV` becomes 2.
4. COUNT 0 passes integrity and is dropped.

The test holds the crypto task back with the suite's manual crypto executor. In practice: a PDU that fills a reordering gap within about one crypto-processing time before expiry is lost. This is more likely under a loaded crypto pool, and on the default UM 5QIs, which use a 1 ms t-Reordering.

## Reproduced

On `dev` 8fe05a213f, Debug and Release builds. The test below asserts the correct behaviour and fails on current code. I have not tested a fix.

## Impact

One UL SDU is lost per occurrence on the affected bearer, with only a debug log. For AM, the loss is final at PDCP because RLC has already acknowledged the PDU. No crash.

## Suggested fix

Track the COUNTs that have been submitted to crypto but not yet reordered. When t-Reordering expires while one of them is below `RX_REORD`, defer the expiry handling until they complete, e.g. with the token mechanism that `await_rx_crypto_tasks()` uses.
