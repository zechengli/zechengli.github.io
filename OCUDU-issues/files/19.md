Title: RLC AM TX: t-PollRetransmit does not trigger a RETX when the shared TX window pool is exhausted
Labels (suggested): bug, rlc

---

## Summary

All AM DRBs of a cell share one `rlc_drb_tx_window_seg_pool`. When it is exhausted, `build_new_pdu()` cannot place the next SDU and returns 0 bytes:

```cpp
// lib/rlc/rlc_tx_am_entity.cpp:266-268
if (!tx_window.add_sn(st.tx_next)) {
  logger.log_warning("Cannot build data PDU, tx_window segment pool is exhausted. grant_len={}", grant_len);
  return 0;
```

`on_expired_poll_retransmit_timer()` (`:1187`) only schedules a RETX if both queues are empty or `is_tx_window_full()`, and `is_tx_window_full()` (`:1234`) only looks at the SN window and `max_window`, not at the pool. So with a new SDU queued that cannot be placed, the timer expiry does nothing, and every following grant returns 0 bytes, although the unacknowledged SDUs already in the window could be retransmitted without a new pool segment. TS 38.322 5.3.3.4 asks for a retransmission "if no new RLC SDU or RLC SDU segment can be transmitted (e.g. due to window stalling)".

## Trigger

1. Bearer A sends SN 0 and SN 1 (poll set, t-PollRetransmit running); nothing is ACKed.
2. Bearer B on the same cell takes the last free pool segment.
3. Bearer A receives SN 2, which needs a new segment.
4. t-PollRetransmit of bearer A expires; the next grant to bearer A returns 0 bytes.

In practice: many DRBs with large amounts of unacknowledged data on one cell (the default pool is 2048 segments of 256 SNs). The test shrinks the pool to 2 segments of 2 SNs.

## Impact

While the pool stays exhausted, the bearer wastes its grants and its unacknowledged SDUs get no poll retransmission, so a lost last PDU is not recovered. No crash; it recovers once another bearer frees a segment.

## Suggested fix

In `on_expired_poll_retransmit_timer()`, also treat "the next SDU cannot be placed because the pool has no free segment" as "no new SDU can be transmitted" and schedule the RETX of `tx_next_ack`. I have not tested a fix.
