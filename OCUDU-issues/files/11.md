Title: PDCP RX: RCVD_HFN underflows in the first hyperframe (one PDU triggers max COUNT and bearer release)
Labels (suggested): bug, pdcp

---

## Summary

`handle_data_pdu()` computes `RCVD_HFN = HFN(RX_DELIV) - 1` in `uint32_t` when `RCVD_SN >= SN(RX_DELIV) + Window_Size`. During a bearer's first hyperframe (`HFN(RX_DELIV) == 0`), this wraps to `0xFFFFFFFF`. The resulting COUNT (e.g. `0xFFFFF800` for SN 2048 with a 12-bit SN) is above both max COUNT thresholds:

```cpp
// lib/pdcp/pdcp_entity_rx.cpp:338-339, handle_data_pdu()
  } else if (hdr.sn >= SN(st.rx_deliv) + window_size) {
    rcvd_hfn = HFN(st.rx_deliv) - 1;          // <- 0xFFFFFFFF when HFN(RX_DELIV) == 0
```

The entity then calls `on_max_count_reached()` and `on_protocol_failure()`. In the CU-UP, both lead to an E1AP Bearer Context Release Request for the UE (`cu_up_manager_impl.cpp:202-218`, `:238-254`). The spec gives no valid HFN below 0. Such a COUNT would be below `RX_DELIV`, and 5.2.2.1 discards PDUs with `RCVD_COUNT < RX_DELIV`.

## Trigger

1. A new 12-bit SN DRB (`RX_DELIV = 0`) with the default max COUNT thresholds.
2. Its first received PDU has SN 2048.

In practice: at least one full window (2048 PDUs for 12-bit SN, which the default QoS table uses for the delay-critical UM 5QIs) of consecutive UL PDUs lost early in a bearer's life. This is uncommon, but it should cost one PDU, not the bearer context.

## Impact

A single UL PDU makes the CU-UP request release of the owning UE's bearer context, and the log reports "Reached max_count" on a bearer that has received almost nothing. Other UEs are not affected.

## Suggested fix

Follow the spec and discard the PDU: in the `>=` branch, if `HFN(st.rx_deliv) == 0`, count it as dropped and return before computing the COUNT and before the max COUNT checks. Do not reinterpret it as a different COUNT. With this change the test passes, and the existing `pdcp_rx_*` tests still pass.
