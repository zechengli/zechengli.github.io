What Phase 1 found: the same rule, implemented more than once

This is the first Specula case study on business software rather than a protocol stack — the contracts are not 3GPP specifications but the eligibility rules, budget arithmetic and approval gates of a public benefits program. The audit's central result is that the dominant defect mechanism here is not classical concurrency at all. It is duplicate authority: the same program rule is implemented two or three times — once in VB.NET as string-concatenated SQL, again as a T-SQL stored procedure, again in a program-year fork — and the copies have drifted apart. Whichever runs last wins.

Discovery 1 — eligibility is decided twice, on different inputs ClientAllocationLogic.UpdateClientAllocationID (:45) decides eligibility using family size = count(FamilyMemberID) over tblLHFamilyInfo, scanning every allocation in the program year, and yields PriorityLevel ∈ {1, −1}. SP_CalcPriorityLevel.sql re-decides the same flag using tblClientInfo.Occupants and only the client's already-stored AllocationID, yielding {1, 0, −1}. Both UPDATE tblClientInfo. When the two family-size sources disagree, so can the verdict.
Discovery 2 — the denial path still writes an allocation When a client's income exceeds every income line, the code does not stop: it falls back to the lowest allocation (:47), sets PriorityLevel = -1 (:74), and then reaches an unconditional update tblClientInfo set AllocationID=… (:84). The denial is returned only ByRef, for the caller to persist or ignore — while the allocation write is immediate. SP_CalcPriorityLevel then reads that fallback value back as the basis of its own eligibility test.
Discovery 3 — there are two different UpdateBalance methods ClientAllocationLogic.UpdateBalance (:207) runs three statements on the caller's transaction, sums as sum(round(x,2)), and inserts missing county rows. frmParishBudget.UpdateBalance (frmParishBudget.aspx.vb:855) runs two statements with no transaction at all, sums as round(sum(x),2), and inserts nothing. They disagree on atomicity, on rounding order, and on coverage — and a payment screen (frmRequestPayment.aspx.vb:207) calls the untransacted one. In that path the spend-valued intermediate state is committed: if the request dies between the two statements, the column reads as a balance but holds the spend, permanently.
Discovery 4 — the negative-balance patch is a confession CheckNegativeBalance was added 02/12/2013 with the comment "Balance should not be negative" — a runtime guard bolted on after the fact, evidence that negative balances were seen in production. It is a detector: it runs a SELECT and returns a value. Whether anything is prevented depends entirely on each caller acting on it.
Discovery 5 — a scorer that can return the caller's own input HighUseHighBurden.GetHighUseAndHighBurden emits a literal 1 As HighBurden when income is zero (:33), bypassing the threshold comparison entirely. Its legacy branch sets high-burden on zero income and Exit Functions before the feature gate (:78), so the flag is set even when the rule is switched off. And when isHighBurdenActive() is false there is no Else (:86) — HighBurden is ByRef, so the scorer silently returns whatever the caller passed in. The function is declared As Integer and never assigns a return value: it is always 0.
Discovery 6 — a correction applied to one copy only BenefitMatrixOf108.vb's own change history records item 4 (12/04/2012, Karen): "The income should be the total income not only one single family member's income." That fix uses SUM(tblClientIncome.AnnualIncome). CalPovertyLevel.vb and SP_UpdateClientPovertyLevelCal.sql still read the single tblClientInfo.AnnualIncome column. The same pattern repeats with family size: a 8/12/2010 patch changed count(*) to count(FamilyMemberID) in ClientAllocationLogic, while BenefitMatrixOf108 still uses COUNT(*).

Archaeology without a repository

There is no git history and no issue tracker here — this is a private source drop, not a checkout. The equivalent evidence base is the in-source patch record: 2,262 dated patch comments plus per-file Item / Date / Author / Bugs Fixed / Description change-history headers carrying Mantis issue numbers (#1247, #2177, #1227, #0002213, #0008214). A patch comment tells us that a fix was made and when, rarely the failing scenario, so each is used only for what it literally says.

What the run was asked to verify

The five priority questions in the guidance file, each pairing a trigger with an observable outcome and the intended contract:

QTrigger → can it happen?Contract
1 A client's income exceeds every income line for the program year → can the client hold a qualified allocation while marked eligible — or be denied while holding one? Eligibility flag and stored AllocationID stay mutually consistent after every update
2 Invoices issue against a county budget, then UpdateBalance recomputes → can balances diverge from budget − Σ rounded invoices, or go negative? After every completed recompute, each balance equals budget minus rounded invoice sum; no completed check observes a negative balance
3 Annual income is 0, or income/fuel-usage rows are missing → can the scoring paths classify the same client inconsistently? Zero/missing income is classified identically by every scoring path
4 A job's allocation window has expired or not started → can it avoid the approval requirement and still progress to payment? Any job outside its allocation window carries Approval=1 and cannot reach payment without state approval
5 The dynamic validity framework evaluates a save → can a record persist with fields failing the configured checks, or be bypassed by ordering? Every persisted record satisfies all applicable configured validity conditions

What a checked invariant looks like

The first is the two-writer disagreement formalised — the stored procedure's Isnull(IncomeLine,0) is the operative clause; the second is the ByRef defect expressed by self-composition, asserting that a scorer's verdict must be a function of the client's data and not of the caller's:

eligibility.tla / scoring.tla — bug detectors
SpIncomeLine ==
    IF lineExists[<<storedAlloc, occupants>>]
      THEN lineValue[<<storedAlloc, occupants>>]
      ELSE 0                      \* Isnull(IncomeLine,0) - a missing row denies

EligibilityWritersAgree ==
    (BothRan /\ spPriority /= 0) => (vbPriority = spPriority)

BurdenIndependentOfCaller ==
    scored => (BurdenWith(0) = BurdenWith(1))

MC-9 (the validity framework, Q5) has no spec, and will not get one — not because the data was unavailable, but because the mechanism turned out not to exist as a live code path. Full call-graph tracing found that ValidityCommand and ValidityConditions, the only two places that call ValidityCheck.GetInstance, are never instantiated anywhere in the 1,399-file source tree — no direct construction, no reflection, no .aspx markup reference. Even were it reachable, the surviving use of a checker instance is GetClientScript, which emits browser-side JavaScript, not a server-side check — it was never a persistence gate. Q5 closes as a negative result: this correction was made after the original Phase 1 pass had wrongly assumed the framework was live.

Findings: 8 confirmed, by code semantics

How these were confirmed — read this before the table Every finding below was produced by a TLC counterexample and then traced back to the VB.NET or T-SQL lines that produce it, all of which were read directly. None was executed. OldSource2 is .NET Framework WebForms and needs Windows, IIS and SQL Server; it cannot be built or run on the host this ran on. The srsRAN case study reproduced every confirmed bug against running C++ through its public APIs — this run cannot make that claim, and the severities below should be read as severity-if-triggerable, resting on a source reading rather than on a reproduction.
IDFindingBasisSeverity
MC-3 A blank or stale tblClientInfo.Occupants silently converts an eligible applicant into a denied one: SP_CalcPriorityLevel re-tests eligibility using Occupants, finds no tgAllocationIncomeLine row for that family size, and Isnull(IncomeLine,0) reads the income limit as zero — so any income at all "exceeds" it. MC-5b Two invoices of $0.001 and $0.004 produce $0.00 spent under ClientAllocationLogic.UpdateBalance (sum(round(x,2))) and $0.01 spent under frmParishBudget.UpdateBalance (round(sum(x),2)). MC-5c frmParishBudget.UpdateBalance runs its two statements on CONN_STRING_LOCAL with no transaction, so the spend-valued intermediate state is committed and readable by every other session. If the request fails in between, the column stays spend-valued indefinitely while its name and every reader treat it as a remaining balance. A payment screen calls this path counterexample + source high
MC-4 A county balance can go negative and be observed there. CheckNegativeBalance — added 02/12/2013 with the comment "Balance should not be negative" — detects this rather than preventing it, and is declared with no As Boolean return type counterexample + source high
MC-8 A job whose allocation window has expired can reach payment without approval, by three distinct routes: payment before the window check ever runs; JobID = "", which returns False before any check; and a job already carrying Approval = 0, which the (Approval is null or Approval=1) predicate cannot see counterexample + source high
MC-6 GetHighUseAndHighBurden returns the caller's own prior value as a scoring result: HighBurden is ByRef and the isHighBurdenActive() branch has no Else. The function is also declared As Integer and never assigns a return value, so its point score is always 0 counterexample + source medium
MC-7 A zero-income client is scored maximum burden by HighUseHighBurden (a literal 1 As HighBurden, skipping the threshold comparison) and lowest poverty group by CalPovertyLevel — which also writes 0 when no tgFederalPovertyLevel row exists, making "no reference data" indistinguishable from "genuinely poorest" counterexample + source medium

The pattern across all eight is one mechanism, not eight: the same program rule is implemented more than once, and the copies have drifted. Eligibility is decided twice on different family-size columns; the budget is recomputed by two methods that disagree on rounding, atomicity and coverage; poverty is computed three ways, and a 12/04/2012 correction ("the income should be the total income not only one single family member's income") was applied to exactly one of them. None of this requires a race — most of the counterexamples have no concurrency in them at all. It requires only that a user reach the same record through two different screens, which is what the application is for.

结果总结(中文)

本次运行把一套运行了十五年的 LIHEAP(低收入家庭能源补助)业务系统——约 1,400 个文件的 VB.NET / ASP.NET WebForms 加 T-SQL 存储过程——中决定"谁能拿到取暖补助、拿多少"的逻辑, 翻译成 TLA+ 并用 TLC 做有界模型检验。共写了三个规约、九条不变式, 其中八条被证伪,每条都有具体反例;最大状态空间 5,660 万个状态。

核心结论只有一句:同一条业务规则被实现了不止一次,而这些副本已经彼此漂移。 资格审核有两套实现——VB 用 count(FamilyMemberID) 统计家庭人数,存储过程用 tblClientInfo.Occupants;两者不一致时,结论就不一致,而数据库里留下的是"最后写入者"的判断。 更严重的是,存储过程里的 Isnull(IncomeLine,0) 会把"查不到对应收入线记录"当成"收入线为零", 于是任何收入都算超标——一个 Occupants 字段填错或为空的申请人,会被静默拒绝, 尽管另一条路径已经判定他合格。

县级预算同样有两个 UpdateBalance:一个走调用方事务、逐张发票四舍五入再求和; 另一个完全不开事务、先求和再四舍五入,而且付款界面调用的正是后者。 两张 $0.001 和 $0.004 的发票,一个算出支出 $0.00,另一个算出 $0.01——不需要任何并发。 不开事务的那条路径还会把"中间状态"直接提交:此刻余额列里存的是支出而不是余额, 若请求在两条语句之间失败,这个错误状态就永久留在库里。2013 年 2 月加的 CheckNegativeBalance(注释写着"Balance should not be negative")只是事后探测,并不能阻止。

必须说明的限制:本次没有做执行级复现。该系统是 .NET Framework WebForms, 需要 Windows + IIS + SQL Server 才能构建运行,本次运行的主机做不到。 所有结论都是"模型检验反例 + 逐行源码核对",而不是像上一个 srsRAN 案例那样在真实运行的代码上复现。 因此上表的严重程度应理解为"若可触发则如此",其依据是源码阅读,而非复现实验。
