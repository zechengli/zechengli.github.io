What Phase 1 found: the same rule, implemented more than once

This is the first Specula case study on business software rather than a protocol stack — the contracts are not 3GPP specifications but the eligibility rules, budget arithmetic and approval gates of a public benefits program. The audit's central result is that the dominant defect mechanism here is not classical concurrency at all. It is duplicate authority: the same program rule is implemented two or three times — once in VB.NET as string-concatenated SQL, again as a T-SQL stored procedure, again in a program-year fork — and the copies have drifted apart. Whichever runs last wins.

Discovery 1 — eligibility is decided twice, on different inputs ClientAllocationLogic.UpdateClientAllocationID (:45) decides eligibility using family size = count(FamilyMemberID) over tblLHFamilyInfo, scanning every allocation in the program year, and yields PriorityLevel ∈ {1, −1}. SP_CalcPriorityLevel.sql re-decides the same flag using tblClientInfo.Occupants and only the client's already-stored AllocationID, yielding {1, 0, −1}. Both UPDATE tblClientInfo. When the two family-size sources disagree, so can the verdict.
Discovery 2 — the denial path still writes an allocation When a client's income exceeds every income line, the code does not stop: it falls back to the lowest allocation (:47), sets PriorityLevel = -1 (:74), and then reaches an unconditional update tblClientInfo set AllocationID=… (:84). The denial is returned only ByRef, for the caller to persist or ignore — while the allocation write is immediate. SP_CalcPriorityLevel then reads that fallback value back as the basis of its own eligibility test.
Discovery 3 — there are two different UpdateBalance methods ClientAllocationLogic.UpdateBalance (:207) runs three statements on the caller's transaction, sums as sum(round(x,2)), and inserts missing county rows. frmParishBudget.UpdateBalance (frmParishBudget.aspx.vb:855) runs two statements with no transaction at all, sums as round(sum(x),2), and inserts nothing. They disagree on atomicity, on rounding order, and on coverage — and a payment screen (frmRequestPayment.aspx.vb:207) calls the untransacted one. In that path the spend-valued intermediate state is committed: if the request dies between the two statements, the column reads as a balance but holds the spend, permanently.
Discovery 4 — the negative-balance patch is a confession CheckNegativeBalance was added 02/12/2013 with the comment "Balance should not be negative" — a runtime guard bolted on after the fact, evidence that negative balances were seen in production. It is a detector: it runs a SELECT and returns a value. Whether anything is prevented depends entirely on each caller acting on it.
Discovery 5 — a scorer that can return the caller's own input HighUseHighBurden.GetHighUseAndHighBurden emits a literal 1 As HighBurden when income is zero (:33), bypassing the threshold comparison entirely. Its legacy branch sets high-burden on zero income and Exit Functions before the feature gate (:78), so the flag is set even when the rule is switched off. And when isHighBurdenActive() is false there is no Else (:86) — HighBurden is ByRef, so the scorer silently returns whatever the caller passed in. The function is declared As Integer and never assigns a return value: it is always 0.
Discovery 6 — a correction applied to one copy only BenefitMatrixOf108.vb's own change history records item 4 (12/04/2012, Karen): "The income should be the total income not only one single family member's income." That fix uses SUM(tblClientIncome.AnnualIncome). CalPovertyLevel.vb and SP_UpdateClientPovertyLevelCal.sql still read the single tblClientInfo.AnnualIncome column. The same pattern repeats with family size: a 8/12/2010 patch changed count(*) to count(FamilyMemberID) in ClientAllocationLogic, while BenefitMatrixOf108 still uses COUNT(*).

Archaeology without a repository

There is no git history and no issue tracker here — this is a private source drop, not a checkout. The equivalent evidence base is the in-source patch record: 2,262 dated patch comments plus per-file Item / Date / Author / Bugs Fixed / Description change-history headers carrying Mantis issue numbers (#1247, #2177, #1227, #0002213, #0008214). A patch comment tells us that a fix was made and when, rarely the failing scenario, so each is used only for what it literally says.

What the run was asked to verify

The five priority questions in the guidance file, each pairing a trigger with an observable outcome and the intended contract:

QTrigger → can it happen?Contract
1 A client's income exceeds every income line for the program year → can the client hold a qualified allocation while marked eligible — or be denied while holding one? Eligibility flag and stored AllocationID stay mutually consistent after every update
2 Invoices issue against a county budget, then UpdateBalance recomputes → can balances diverge from budget − Σ rounded invoices, or go negative? After every completed recompute, each balance equals budget minus rounded invoice sum; no completed check observes a negative balance
3 Annual income is 0, or income/fuel-usage rows are missing → can the scoring paths classify the same client inconsistently? Zero/missing income is classified identically by every scoring path
4 A job's allocation window has expired or not started → can it avoid the approval requirement and still progress to payment? Any job outside its allocation window carries Approval=1 and cannot reach payment without state approval
5 The dynamic validity framework evaluates a save → can a record persist with fields failing the configured checks, or be bypassed by ordering? Every persisted record satisfies all applicable configured validity conditions

A note on Phase 2.5 Harness generation — instrumenting the target to emit execution traces — is skipped for this run, and not by preference. OldSource2 is .NET Framework WebForms: building and running it needs Windows, IIS and SQL Server, which this macOS host cannot provide. Trace validation against real executions is therefore unavailable, and Phase 4 confirmation will be code-semantics confirmation — each counterexample replayed against the VB.NET and T-SQL source with file:line citations, not executed. That is a real limitation of this run and is stated here rather than buried: the srsRAN case study reproduced every confirmed bug against running C++; this one cannot.
