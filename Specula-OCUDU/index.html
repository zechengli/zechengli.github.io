Formal methods · Specula × OCUDU

TLA+ model checking OCUDU's RLC, PDCP and RRC

Specula was pointed at OCUDU, the Linux Foundation successor of the srsRAN Project CU/DU, and asked whether its layer-2/3 protocol machinery (RLC AM, PDCP, and the CU-CP's per-UE RRC procedures) can reach states that violate the 3GPP contracts it implements (TS 38.322, 38.323, 38.331) under realistic concurrency between executors. This is the same code base as the srsRAN Project case study, ten months and one rename later: the target here is OCUDU main at 9c99f4064, after release 26.04.

Six bugs were reproduced against the unmodified C++ through its public APIs. Two of them are reachable from a single peer message or a single legal E1AP request: a DU process crash from one STATUS PDU (MC-5) and a heap use-after-free in the CU-UP (MC-3).

What the audit found first

OCUDU is not a UE. The guidance framed lib/rrc/ue/ as UE RRC procedures with T310/N310/N311. Phase 1 corrected this: OCUDU is gNB-only, and lib/rrc/ue/ is the CU-CP's per-UE context, the network's peer to the real UE's RRC. Its T300/T301/T304/T311 values are timeouts on how long the network waits for the UE, and a repository-wide search for t310/n310 under lib/rrc/ue returns nothing. RLF detection lives in the MAC (rlf_detector.h) and in the DU's UE controller, and was modeled there.

The risk is concurrency, not just protocol logic. Every state machine runs as handlers spread over independent executors: a MAC-driven cell executor, a per-UE executor (a three-level priority strand for PDCP), and a genuinely parallel crypto worker pool for PDCP ciphering and integrity. Most findings below are stale-completion or unguarded-access bugs whose visible effect is a protocol violation.

MC-5 · One STATUS PDU crashes the DU

handle_nack() accepts any NACK with TX_Next_Ack ≤ NACK_SN ≤ TX_Next and then indexes tx_window without checking that the SN is present. TX_Next itself has never been submitted, so a STATUS PDU with ACK_SN = 1 and NACK_SN = 0 on a fresh entity dereferences an empty slot. The confirmer drove exactly this through the real on_status_pdu → handle_status_pdu → handle_nack chain: SIGSEGV in 5 of 5 runs, while the adjacent boundary (NACK_SN = ACK_SN) is correctly rejected. On a gNB the STATUS PDU comes from the UE, so the input is peer-controlled and needs no non-conformant behavior. Suggested fix: check tx_window.has_sn() before the access, as build_retx_pdu already does.

MC-3 · Use-after-free in the CU-UP crypto path

A bearer-context modification that asks for PDCP re-establishment but carries no SecurityInformation, a legal E1AP combination, skips the step that waits for in-flight crypto jobs. Re-establishment then clears the security engine pool while crypto workers still use it. AddressSanitizer reported a heap use-after-free in integrity_engine_generic.cpp:60 in 3 of 3 runs (one run hit s3g.cpp:479 instead), using only the public API and a real two-thread executor. Without the sanitizer the outcome is a corrupted PDU on the air or a CU-UP crash. Suggested fix: drain regardless of SecurityInformation, or move the drain into reestablish() itself using the existing crypto token manager.

MC-7 · An SDU that is ACKed but never delivered

When reassembly fails, for example because the buffer pool is exhausted, the RX entity logs "Dropped SDU, failed to reassemble", keeps fully_received = true, advances the window and ACKs the SN (the next STATUS PDU has ACK_SN = 1 and no NACK). The peer's retransmission then arrives outside the window and is discarded. The SDU is lost permanently and silently. Reproduced in the project's own RLC RX test suite for both 12- and 18-bit SNs. Suggested fix: clear fully_received on the failure branch so the SN stays NACK-eligible.

MC-4 · Stale crypto results after a reset

suspend() and reset() do not advance the generation counter that fences crypto completions (retransmit_id). A completion for a job started before re-establishment can land after it and overwrite the window slot of a new SDU with the same COUNT. On TX a stale PDU is sent and the new SDU stays stuck; on RX the new SDU is dropped as a duplicate. The trigger is again re-establishment without SecurityInformation, where the real caller performs no drain.

MC-2 · A reestablishment flag that never clears

When a reestablishment request finds the old UE fully attached (DRB and SRB2 up) and the context transfer fails, the procedure falls back to RRCSetup, but the old UE's reestablishment_ongoing flag, set by get_context(), is never written back to false on any path. A later reestablishment for the same UE is refused again and answered with RRCSetup over SRB0 instead of RRCReestablishment over SRB1. The flag's introduction carries a // TODO: Handle scenario with multiple reestablishments for the same UE.

MC-6 · Retransmitting past maxRetxThreshold

A single STATUS PDU with NACKs [1][3][1] increments RETX_COUNT for SN 1 twice, because duplicate suppression only compares with the previous NACK. The max-retx check tests retx_count == threshold, so the count jumps past it: after on_max_retx has fired, pull_pdu() still hands the MAC a retransmission with RETX_COUNT 5 > 4. For an SRB nothing downstream stops it, since the DU's RLF reaction stops only DRBs.

Not counted

MC-8 is a fault-model artifact: the spec runs SRB crypto asynchronously, but in OCUDU only DRBs have a parallel crypto executor, and SRBs use an inline one. The confirmer filed a repair request against the model rather than the code. CR-1 is a false positive: the notifier pointer is only written on the control strand, so no torn read is possible through real callers. MC-1 was interrupted during confirmation and has no verdict.

Reading the findings through history

The checker says what the code can do today. The git history says how it got there. Three findings have a history worth telling, checked against the OCUDU repository.

MC-7 came from a careful decision. The branch that drops a failed SDU was added by d6950cfed (2024-02-23, "rlc_rx: handle reassembly failures"), whose own comment reads "Do not pass empty SDU to upper layers and continue as normal to maintain state." Degrading gracefully instead of crashing is the right instinct; continuing "as normal" is what ACKs the missing SDU. The branch has been on main for 937 days.

MC-5's check is as old as NACK handling. The inclusive range test TX_Next_Ack ≤ NACK_SN ≤ TX_Next is unchanged since NACK handling was added in 415c5f9ee (2022-08-16). Whether the out-of-window access always crashed, or only after the RLC window was rewritten (4ab518f6a, 2026-06-26), is still open; answering exactly this kind of question is what a history-aware checker should do. The confirmer also notes that the RX side already received a presence check of the same shape; in the history, 5fe74a8ca (2026-08-13) adds such a has_sn() guard on the RX entity, while the TX side remained unguarded.

A known bug this run did not report. The earlier srsRAN Project run confirmed that one rejected t-StatusProhibit defer latches a "timer running" flag and stops STATUS reporting for good (its MC-3). The same code is still at OCUDU 9c99f4064 (rlc_rx_am_entity.cpp, get_status_pdu()), and on 2026-08-13 commit a1491504c fixed the same pattern for buffer-state notifications on the TX side only. This run's model did not produce it. Agentic runs on the same code are not interchangeable, which is one more reason to keep findings, once confirmed, as permanent obligations.
