Crypto: what each key depends on


Everything starts from one secret, K (128 bits), stored in the SIM and in the network's subscriber database. It is never sent.


K, OPc, RAND, SQN                 --Milenage-->   MAC, RES, CK, IK, AK
AUTN = SQN xor AK, AMF field, MAC                 sent to the phone together with RAND

CK, IK, network name, SQN xor AK  -->  K_AUSF
CK, IK, network name, RAND, RES   -->  RES*   (phone)   =   XRES*  (network)
RAND, XRES*          --SHA-256--> HXRES*                 the only part the AMF is given

K_AUSF, network name -->  K_SEAF
K_SEAF, SUPI, ABBA   -->  K_AMF
K_AMF                -->  K_NASint, K_NASenc             protect phone-to-AMF messages
K_AMF                -->  K_gNB                          protects the radio link


    
  
  • Phone verifies network: the SIM recomputes MAC from K, RAND and SQN and compares it with the MAC inside AUTN. Only a network that knows K can produce it.
    • 
  
  • Network verifies phone: only a SIM that knows K can produce RES*. The AMF compares SHA-256 of it with HXRES*, and the AUSF compares RES* with XRES*.
    • 
  
  • Who computes what: UDM: Milenage, XRES*, K_AUSF. AUSF: HXRES*, K_SEAF. AMF: K_AMF, NAS keys, K_gNB. The phone computes all of them on its side.
    • 
  
  • Used in this run: key derivation is HMAC-SHA-256. NAS integrity is NIA2 (AES). NAS ciphering is NEA0 (none), the default order of this core.
    • 
  
  • The nonce is not part of this chain.
    •

Why this small version is enough


    
  
  • We wrote none of the crypto and none of the message encoding. Paging, 5G-AKA and the key chain are the existing, standard code.
    • 
  
  • The 303 lines do one thing: when a page was asked for through the API, run a fresh 5G-AKA before accepting the phone's answer, and report pass or fail.
    • 
  
  • The messages and keys are the same ones a real network uses. Only the radio below RRC is simulated. Going on the air replaces that bottom layer and nothing above it.
    • 
  
  • Both outcomes are shown: right key passes, wrong key fails, no answer fails.
    • 



What it does not do: real paging occasions (the simulator pages at once), more than one cell, encryption of NAS messages (NEA0), and a nonce shown on a different device from the one it is typed on.

Flow


    
  
  1. Write IMSI, K and OPc to the SIM. Add the same subscriber to Open5GS.
    2. 
  
  2. Start Open5GS.
    3. 
  
  3. Start the srsRAN gNB on the B210 with the same network code and tracking area.
    4. 
  
  4. Put the SIM in the phone. It registers and gets an IP address.
    5. 
  
  5. Leave the phone alone until the cell releases it. It is now idle.
    6. 
  
  6. call: ping the phone's IP. The page goes out over the air at the phone's real paging occasion, and the phone answers.
    7. 
  
  7. verify: the same API. This time the real SIM checks the network and produces RES*.
    8. 
  
  8. nonce: as now.
    9.

Not tested yet


    
  
  • None of the over-the-air steps have been run with this demo. On this PC the srsRAN gNB, a B210 and Open5GS have run together before, with srsUE.
    • 
  
  • A real phone may not accept a new authentication in the middle of a Service Request in the same way the simulated phone does.
    • 
  
  • After a failed verify a real phone treats its SIM as invalid until it is restarted.
    • 
  
  • Transmit only in a shielded box or over cables, unless there is a licence for the band.
